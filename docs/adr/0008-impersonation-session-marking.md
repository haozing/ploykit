# ADR 0008 · impersonation session marking: impersonation state becomes first-class

Status: implemented (2026-10-07); landed within the same change: migration 034 + issue-time write + Principal carry-out + /auth/me exposure + chained-impersonation blocking.

## Background

In impersonation v1 the session was a **fully equivalent session of the target**: the session table carried no impersonation marker, and every operation during the impersonation window (changing email / changing password / creating PATs — credentials that outlive the session) landed in the audit log under the target's identity; afterwards one could only infer correlation from the time window plus the preceding `admin.impersonate` event (with session_token_hash in its meta as corroborating evidence). The damage runs in both directions: a malicious administrator can "act in another's name" to shift blame, and the affected user can deny it with "that was the administrator impersonating me" — a one-way break of non-repudiation.

The privilege-escalation surface was sealed in v1: the target must not be a platform administrator (validated by the admin app `Impersonate`, test-covered), so a normally issued impersonation session cannot pass requireAdmin. But one edge remains: `VerifySession` **re-reads** `is_platform_admin` from the user table on every request, so a target promoted after issuance keeps its lingering impersonation session, which acquires platform-administrator powers along with the promotion until it expires — at that point "impersonating again from an impersonation session" (chained impersonation) holds under guard semantics.

## Decision

Impersonation sessions get a first-class marker, exposed across the whole chain, and their own impersonation right is revoked:

1. **Persistence**: the session table gains `impersonated_by uuid NULL REFERENCES "user"(id)` (migration 034; NULL for normal sessions, the initiating administrator's userID for impersonation sessions). The FK carries no ON DELETE action (same as 028 member.removed_by: account deletion is a soft delete, and hard deletes occur only in tests; CASCADE semantics would actually obscure the fact of "who initiated the impersonation").
2. **Issue-time write**: identity pgrepo gains `CreateImpersonatedSession` (the original `CreateSession` signature stays untouched — it is a webx.SessionStore interface method, and changing the signature would break every implementer and test fake; the new method is purely additive); the admin impersonation path switches to the new method and writes the initiating administrator's ID.
3. **Principal carry-out**: `webx.Principal` gains an `ImpersonatedBy string` field (a platform-generic field, purely additive, breaking no existing consumers); `VerifySession` carries it out of the session row, empty string = normal session. PAT / system origins are always empty.
4. **API exposure**: the `/auth/me` response gains an `impersonated_by` field under impersonation sessions (omitted for normal sessions — byte-level compatible). The frontend "you are in an impersonation session" banner was **not part of this ADR** at landing; it has since shipped as `ImpersonationBanner` in @ploykit/ui (driven by this field, mounted in the AppShell; its tests reference this ADR).
5. **Chained-impersonation blocking (decision)**: the `Impersonate` entry point rejects impersonation initiated by a session whose `p.ImpersonatedBy` is non-empty (403). This also seals the "target promoted after issuance" edge — even if the impersonation Principal passes requireAdmin thanks to the re-read of is_platform_admin, it cannot launch the next impersonation hop. Why entry-point rejection instead of a global requireAdmin rejection (at decision time): a global requireAdmin rejection would strip the promoted target's lingering session of the entire admin surface (including the self-rescue path of kicking its own impersonation session), whereas the chained risk exists only at the "initiate another impersonation" hop; minimal rejection surface + precise 403 semantics (the error message can guide "exit impersonation before operating"). *Current state: the admin adapter's `requireAdmin` has since been tightened to reject impersonated sessions on the whole admin API (403 "admin API is not available to impersonated sessions", guard-tested in admin/adapters/http/routes.go), superseding the self-rescue-path consideration above; the entry-point check in the admin app `Impersonate` remains as defense-in-depth.*
6. **No independent short TTL (decision)**: impersonation sessions reuse the normal session TTL (sliding + absolute cap) and the existing revocation machinery. Rationale: **ending the impersonation is controlled by the initiating administrator** — in a debugging scenario the administrator needs an adequate time window (reproduce the issue, read logs, change configuration); an independent short TTL would instead interrupt the session mid-debugging, forcing the administrator to repeatedly re-initiate impersonation and generating more admin.impersonate event noise; moreover, impersonation sessions are listed and kickable in the target user's "logged-in devices" list (the existing KickSession / RevokeAllSessions machinery), and the list payload carries `impersonated_by` (`SessionInfo`), which together with this ADR's marker makes abuse observable and actionable (the devices-list UI does not yet render the marker). An independent short TTL is an enhancement slot: when needed it goes behind an explicit AuthConfig option, never a default.

## Boundary and non-goals

- No impersonation flag in the audit actor_snapshot (the other half of the fix direction): this change only marks the session side; reworking the audit snapshot touches the audit domain's Principal consumption surface and is a separate project.
- "Exit impersonation and restore the original session": still open frontend work (current v1 semantics: the administrator's original session cookie is overwritten; exiting lands on the login page). The banner itself has landed — `ImpersonationBanner` in @ploykit/ui, shown when impersonated_by is non-empty (decision item 4).
- Impersonation sessions calling the admin surface's other endpoints (impersonation itself excepted): `requireAdmin` rejects impersonated sessions on the whole admin API regardless of the target's admin status, so both the original "target is not an administrator" case and the promotion edge are sealed at the gate (see item 5's current-state note), with audit trails of admin operations as the backstop; no further tightening.

## Consequences

- Positive: impersonation state upgrades from "inferred via audit corroboration" to "self-evident from the session" — /auth/me can be judged mechanically, the session row is directly queryable via SQL, and Principal is consumable along the request chain; chained impersonation is structurally rejected at the entry point.
- Negative: impersonation sessions issued before migration 034 carry no marker (NULL = normal semantics), and the stock transition period is digested naturally by SessionTTL; the /auth/me response shape gains one optional field, so consumer schemas must permit additional fields (the JSON convention allows them by default).
- Revisit point: any new authorization decision consuming ImpersonatedBy must also account for requireAdmin's is_platform_admin re-read semantics; the frontend banner has landed and links back to this ADR (ImpersonationBanner tests); any future surfacing of the marker in the devices-list UI follows the example wiring discipline (page + API + tests, at least three items).
