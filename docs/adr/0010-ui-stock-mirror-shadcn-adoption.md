# ADR 0010 - @ploykit/ui component production: shadcn-generated, then owned (clean-copy)

Status: **implemented** (2026-10-10); all 23 components replaced with shadcn CLI 4.21 output
(base-nova / Base-UI kernel), and the hooks layer split into `@ploykit/hooks` in the same
batch (client -> runtime -> hooks -> ui).

## Background

components/ui was hand-written. Its shape was already isomorphic with modern shadcn output
(Base-UI kernel + cva/cn/oklch tokens), but it was maintained by hand: upstream a11y/bugfixes
could not be tracked systematically, and complex components (sidebar, 19.3 kB) carried high
maintenance cost. Two structural gaps came with it:

- **Export-surface gap**: the exports map only had the root entry; 9 of the 23 components
  (alert-dialog/avatar/breadcrumb/card/checkbox/popover/progress/select/switch) existed in
  dist but were impossible to import from products.
- **Layer mixing**: react hooks/provider lived inside @ploykit/ui next to UI components, so a
  product with its own UI stack (e.g. antd) had to install tailwindcss/base-ui peers just to
  use hooks.

Rejected alternatives:

- **Products run `npx shadcn add` themselves for everything** - rejected: component copies
  scatter across products, framework upgrades cannot reach the copies, and this contradicts
  the repo's anti-duplication clause (AGENTS.md: framework grows a capability -> product-side
  equivalents get cleaned up).
- **Depend on a shadcn component-library npm package** - no such distribution form exists
  (shadcn's own philosophy is copy & own).
- **Keep hand-written + port upstream fixes via diff** - rejected: archaeology-style merging
  costs the most exactly on the components that most need upstream fixes.

## Decision

1. **Ownership**: components/ui belongs to the framework package (same layering as migrations
   001-999); products consume via `@ploykit/ui` (root curated exports or the
   `./components/ui/*` subpath exports).
2. **Production method (clean-copy)**: components are generated by the shadcn CLI and
   overwrite wholesale; `adopt-shadcn.mjs` rewrites import paths (`@/` -> relative, `cn` ->
   own lib/utils) - **the only allowed change**. components.json / tsconfig paths / dev.css
   ship inside the package so future upstream sync = re-add + adopt + diff, where the diff
   can only contain upstream changes.
3. **Adaptation flows one way**: shadcn -> ploykit callers (layouts/pages/business
   components) -> example. Every incompatibility surfaced by tsc/tests is fixed in the
   caller, never by editing stock. Product look-and-feel re-bases on stock semantics.
4. **Carry-over rule**: shadcn has an equivalent -> use stock; it does not -> keep the
   ploykit-specific definition but place it in the business layer (components/, lib/);
   components/ui stays stock (StatusBadge moved out as the worked example).
5. **Stock-mirror invariants** (pinned by a guard test): components/ui must not import
   business concepts (@ploykit/*, provider, pages are all forbidden); gaps are solved by
   lifting into the composition layer - the three ploykit enhancements of the old
   hand-written sidebar (cookie read-back P2-17, input-focus guard P3-1, skeleton
   determinism P2-11) all moved to AppShell or re-pinned to stock semantics with zero
   component changes.
6. **Hooks split**: provider / hooks x16 / realtime / ws-query-bridge / perm moved to
   @ploykit/hooks (zero UI dependencies; peers only react + @tanstack/react-query);
   use-mobile stays in ui (sidebar's UI infrastructure). No compat layer: the ui root index
   no longer re-exports hooks symbols; release order is client -> runtime -> hooks -> ui.
7. **Tokens belong to products**: product CSS (example/web/src/index.css) owns the full
   token set, upgraded to v4 (shadcn/tailwind.css + tw-animate-css), keeping the ploykit
   extension tokens (success/warning/sidebar family); dev.css in the package exists only for
   CLI validation.
8. **AppShell / business components / pages are always framework-owned** and are not
   clean-copy targets; shadcn blocks (full-page layout templates) serve as reference material
   for recomposing AppShell visuals and as the product-side long-tail channel - they never
   enter the framework package.

## Consequences

- Tracking upstream fixes drops from archaeology-style merging to a mechanical diff; a
  future kernel change (e.g. a Base-UI major) re-runs the same generation pipeline.
- Stock-vs-old semantic differences (iconSm -> icon-sm, EmptyFooter -> EmptyContent, random
  sidebar skeleton widths, ...) are absorbed by callers per rule 3, done in the same batch.
- The `npm ls @base-ui/react` single-copy constraint stays in force (products must check
  after CLI adds; see dev-environment.md, "Adding long-tail components from the shadcn CLI").
- @ploykit/hooks needs its npm trusted publisher configured before its first release
  (haozing/ploykit/release.yml, environment empty; first publish within 2 days of
  registering).
